# Change Requests

本目录用于记录 Project0 后续跨文件修改的变更请求（Change Request，简称 CR）。

CR 的作用是让一次变更在执行前明确原因、范围、风险、批准状态和验证结果，避免在治理修复、文档对齐或 P1.3 采购前置清理中出现无边界修改。

## 何时必须建立 CR

以下情况必须先建立 CR：

1. 修改会影响多个文件或多个目录。
2. 修改会影响已确认的阶段路线、文档结构、接口定义、安全约束或验收口径。
3. 修改涉及 README、CHANGELOG、docs、process、hardware 等关键项目文档之间的对齐。
4. 修改需要明确允许修改文件、禁止修改文件、风险和验证方式。

## 何时不需要建立 CR

以下情况通常不需要建立 CR：

1. 单文件内的小错字、格式或链接修正，且不改变事实含义。
2. 按已批准 CR 执行的具体修改。
3. 只读分析、检索、审查和 diff 查看。
4. 不进入仓库的临时讨论、草稿或命令输出。

## CR 与 DEC 的区别

DEC 用于记录已经确认的重要决策、路线选择和决策理由。

CR 用于记录一次变更的执行管理，包括为什么改、改哪里、哪些不能改、如何验证、如何回滚。

CR 不能替代 DEC，也不能用来绕过人工确认修改已确认的 DEC 结论。如需改变已确认 DEC，应先提出明确影响分析，并经人工确认后再处理。

## CR 与 Git commit 的关系

CR 记录变更意图、边界和验证过程。

Git commit 记录实际进入版本历史的文件变更。

一个 CR 可以对应一个或多个 commit；一个 commit 如属于某个 CR，应在 CR 中记录关联 commit。提交前应先确认实际 diff 与 CR 允许范围一致。

## 执行流程

跨文件修改必须遵循：

Plan -> Execute -> Verify -> Commit

1. Plan：只读分析，列出影响范围和允许修改清单。
2. Execute：经人工确认后，只修改批准清单中的文件。
3. Verify：检查是否存在矛盾、越界、遗漏和验证失败。
4. Commit：人工查看 diff 后，再提交到 Git。

## 当前阶段用途

当前阶段为 P1.3 硬件方案与采购。CR 的主要用途是：

1. 治理修复。
2. 文档对齐。
3. P1.3 采购前置清理。

G0 已正式收束后，后续跨文件治理修改仍按本目录现有 CR 流程管理。G0 遗留问题不单独新增治理跟踪文件，后续按 CR / 阶段任务机制逐项承接。

CR 不用于扩大当前阶段范围，不用于提前展开 P2-P6 代码实现或 P7-P10 迭代二研究增强细节。
