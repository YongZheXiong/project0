# AI 工作流规范

## 1. 文件作用

本文档用于规定 Project0 中 AI / Codex / Agent 进入仓库后的操作化工作流。

它服务于只读审计、修改计划、受控执行、diff 检查、提交前验证和提示词使用流程。本文档不定义项目技术事实，不替代 DEC、CR、README、DOC_INDEX、架构文档或 `AGENTS.md`。

长期 AI 协作规则、角色分工、权限边界和 Agent 红线以 `docs/_meta/conventions/ai_collaboration_rules.md` 为准。

## 2. 任务类型与使用方式

### 2.1 只读审计

只读审计用于检查文件状态、事实一致性、目录结构、引用关系和风险点。

规则：

1. 可以读取批准范围内的文件。
2. 不修改文件。
3. 输出问题、影响范围和建议。
4. 不自动进入 Execute。
5. 如发现需要跨文件修改，应建议建立或引用 CR。

### 2.2 修改计划

修改计划用于在 Execute 前明确修改边界。

规则：

1. 列出允许修改文件。
2. 列出禁止修改文件。
3. 说明预期修改目标。
4. 说明风险和验证方式。
5. 涉及跨文件修改时，必须先建立或引用 CR。
6. 计划未经人工确认时，不进入 Execute。

### 2.3 单文件修改

单文件修改适用于小范围错字、格式、状态标注或局部说明修正。

规则：

1. 修改前说明目标文件和修改目的。
2. 只改目标文件。
3. 修改后检查 diff。
4. 如果修改改变事实含义，应按事实源规则处理。

### 2.4 跨文件修改

跨文件修改适用于多个文档之间的事实对齐、引用修复、状态同步或治理收束。

规则：

1. 必须先建立或引用 CR。
2. 必须列出允许修改文件和禁止修改文件。
3. 必须执行 Plan -> Execute -> Verify -> Commit。
4. Agent 只能修改已批准文件。

### 2.5 DEC 修改或废弃

DEC 是技术决策事实源，不能随意修改。

流程要求：

1. 修改 DEC 状态、结论或废弃 DEC 前，必须建立 CR。
2. 必须说明影响哪些规划、架构、部署、实现或采购内容。
3. 不允许 Agent 自动推翻已确认 DEC。
4. 废弃 DEC 时应保留历史可追溯性，不直接抹除决策背景。

### 2.6 README / DOC_INDEX / AGENTS / CHANGELOG 修改

这些文件属于项目治理层，修改时应保持职责清晰。

流程要求：

1. `README.md` 只做仓库入口摘要，不定义新的设计事实。
2. `docs/DOC_INDEX.md` 只做索引和依赖导航，不替代正式文档。
3. `AGENTS.md` 约束 AI / Agent 协作入口，不定义项目技术事实。
4. `CHANGELOG.md` 记录版本变化，不替代设计依据。
5. 修改这些文件之间的治理关系时，必须建立 CR。

### 2.7 P1.3 BOM / 采购清单相关任务

P1.3 当前重点是硬件方案与采购。

流程要求：

1. 先确认已有硬件、缺失硬件、接口需求和安全约束。
2. BOM 与采购清单应承接定义层、规划层、架构层和有效 DEC。
3. 涉及硬件事实、接线、采购优先级或 BOM 字段变化时，必须检查影响范围。
4. 不把 P2-P6 实现细节或 P7-P10 研究增强提前写成 P1.3 必做项。

### 2.8 不进入仓库的临时讨论

临时讨论适用于想法澄清、方案比较、提示词草稿和个人复盘。

规则：

1. 不需要建立 CR。
2. 不修改仓库。
3. 不把讨论内容自动视为项目事实。
4. 若讨论结果需要落库，应再按对应任务类型进入流程。

## 3. Plan -> Execute -> Verify -> Commit

Project0 的跨文件修改统一遵循：

```text
Plan -> Execute -> Verify -> Commit
```

### 3.1 Plan

Plan 是只读分析阶段。

要求：

1. 读取相关文件。
2. 列出影响范围。
3. 列出允许修改文件。
4. 列出禁止修改文件。
5. 说明风险和验证方式。
6. 不修改文件。

### 3.2 Execute

Execute 是受控修改阶段。

要求：

1. 经人工确认后执行。
2. 只修改批准文件。
3. 不扩大目录和阶段范围。
4. 不顺手重写无关内容。
5. 发现范围不足时暂停并回到 Plan。

### 3.3 Verify

Verify 是修改后检查阶段。

要求：

1. 检查事实一致性。
2. 检查是否存在越界修改。
3. 检查是否遗漏必要同步项。
4. 查看 diff。
5. 必要时运行相关验证命令。

### 3.4 Commit

Commit 是进入版本历史阶段。

要求：

1. 人工先审查 diff。
2. 确认变更符合 CR 或批准范围。
3. 再由人工决定是否提交。
4. 提交后记录必要的 CR 或版本关联。

## 4. 什么时候必须建立 CR

以下情况必须建立 CR：

1. 跨文件修改。
2. 修改事实源。
3. 修改 DEC 状态。
4. 修改架构边界。
5. 修改 `README.md`、`docs/DOC_INDEX.md`、`AGENTS.md`、`CHANGELOG.md` 之间的治理关系。
6. 修改会影响 P1.3 采购、BOM、接线或硬件事实。

CR 应说明变更原因、允许修改范围、禁止修改范围、风险、验证方式和结果。CR 不替代 DEC，也不能绕过人工确认去修改已确认决策。

## 5. 什么时候不需要建立 CR

以下情况通常不需要建立 CR：

1. 单文件内的小错字、格式或链接修正，且不改变事实含义。
2. 按已批准 CR 执行的具体修改。
3. 只读分析、检索、审查和 diff 查看。
4. 不进入仓库的临时讨论、草稿或命令输出。

如果不确定是否需要 CR，应先按 Plan 只读分析，说明影响范围后等待人工确认。

## 6. Diff 检查

修改后应检查 diff。

常用检查包括：

1. `git status --short`
2. `git diff --name-only`
3. `git diff --check`
4. `git diff -- <path>`

检查重点：

1. 实际修改文件是否只包含批准范围。
2. 是否改变技术事实、状态含义、日期事实或替代关系。
3. 是否误改 DEC、Architecture、Planning、Definition 或实现层文件。
4. 是否引入空白错误、冲突标记或格式异常。

## 7. 提交前验证

提交前至少确认：

1. `git status --short` 与批准范围一致。
2. `git diff --name-only` 与批准范围一致。
3. `git diff --check` 未出现阻断性问题。
4. CR 已记录执行结果和验证结果。
5. `CHANGELOG.md` 是否需要按当前变更类型更新。
6. 人工已确认是否允许 `git add` 和 `git commit`。

只有 LF / CRLF warning 时，不自动视为阻断；是否处理换行问题应按本次任务边界决定。

## 8. Agent 提示词使用流程

需要让 Agent 执行仓库任务时，提示词应尽量明确：

1. 当前任务名称或 CR 编号。
2. 当前阶段是 Plan、Execute、Verify 还是 Commit。
3. 允许修改文件。
4. 禁止修改文件。
5. 目标和非目标。
6. 验证命令。
7. 是否允许 `git add`。
8. 是否允许 `git commit`。

如果提示词只要求只读审计，Agent 不应自行修改文件。

如果提示词允许 Execute，Agent 仍应只修改批准范围内的文件，并在完成后输出 diff、验证结果和剩余风险。
