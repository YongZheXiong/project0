# AI 工作流规范

## 1. 文件作用

本文档用于规定 Project0 中对话式 AI、Codex / Agent、人工决策和 Git 的分工。

它服务于当前单人 solo 开发、对话式 AI 辅助分析、Codex / Agent 受控执行、Git 留痕回滚的工作方式。本文档不定义项目技术事实，不替代 DEC、CR、README、DOC_INDEX 或架构文档。

## 2. AI 使用角色分工

### 2.1 对话式 AI

对话式 AI 主要用于不直接进入仓库的思考和整理，包括：

1. 路线讨论；
2. 方案分析；
3. 复杂判断；
4. 提示词设计；
5. 复盘总结。

对话式 AI 可以帮助形成思路，但不能直接替代 DEC 结论、CR 范围、人工批准或 Git 提交。

### 2.2 Codex / Agent

Codex / Agent 主要用于仓库内的文件级工作，包括：

1. 仓库读取；
2. 只读审计；
3. 受控修改；
4. diff 检查；
5. 文件级执行。

Codex / Agent 必须先理解当前阶段、允许范围和禁止范围，再执行修改。涉及跨文件变更时，必须遵循 Plan -> Execute -> Verify -> Commit。

### 2.3 人工

人工负责最终控制权，包括：

1. 最终决策；
2. 批准修改范围；
3. 审查 diff；
4. 决定是否提交。

AI 可以提出建议、列风险、执行批准范围内的修改，但不能代替人工确认关键边界。

### 2.4 Git

Git 负责工程状态管理，包括：

1. 隔离分支；
2. 提交记录；
3. 回滚；
4. 合并。

Git 历史应反映真实变更，不用提交记录掩盖未审查、越界或事实不一致的修改。

## 3. 任务类型与使用方式

### 3.1 只读审计

只读审计用于检查文件状态、事实一致性、目录结构、引用关系和风险点。

规则：

1. 可以读取批准范围内的文件；
2. 不修改文件；
3. 输出问题、影响范围和建议；
4. 不自动进入 Execute。

### 3.2 单文件修改

单文件修改适用于小范围错字、格式、状态标注或局部说明修正。

规则：

1. 修改前说明目标文件和修改目的；
2. 只改目标文件；
3. 修改后检查 diff；
4. 如果修改改变事实含义，应按事实源规则处理。

### 3.3 跨文件修改

跨文件修改适用于多个文档之间的事实对齐、引用修复、状态同步或治理收束。

规则：

1. 必须先建立或引用 CR；
2. 必须列出允许修改文件和禁止修改文件；
3. 必须执行 Plan -> Execute -> Verify -> Commit；
4. Agent 只能修改已批准文件。

### 3.4 DEC 修改或废弃

DEC 是技术决策事实源，不能随意修改。

规则：

1. 修改 DEC 状态、结论或废弃 DEC 前，必须建立 CR；
2. 必须说明影响哪些规划、架构、部署、实现或采购内容；
3. 不允许 Agent 自动推翻已确认 DEC；
4. 废弃 DEC 时应保留历史可追溯性，不直接抹除决策背景。

### 3.5 README / DOC_INDEX / AGENTS / CHANGELOG 修改

这些文件属于项目治理层，修改时应保持职责清晰。

规则：

1. `README.md` 只做仓库入口摘要，不定义新的设计事实；
2. `docs/DOC_INDEX.md` 只做索引和依赖导航，不替代正式文档；
3. `AGENTS.md` 约束 AI / Agent 协作方式，不定义项目技术事实；
4. `CHANGELOG.md` 记录版本变化，不替代设计依据；
5. 修改这些文件之间的治理关系时，必须建立 CR。

### 3.6 P1.3 BOM / 采购清单相关任务

P1.3 当前重点是硬件方案与采购。

规则：

1. 先确认已有硬件、缺失硬件、接口需求和安全约束；
2. BOM 与采购清单应承接定义层、规划层、架构层和有效 DEC；
3. 涉及硬件事实、接线、采购优先级或 BOM 字段变化时，必须检查影响范围；
4. 不把 P2-P6 实现细节或 P7-P10 研究增强提前写成 P1.3 必做项。

### 3.7 不进入仓库的临时讨论

临时讨论适用于想法澄清、方案比较、提示词草稿和个人复盘。

规则：

1. 不需要建立 CR；
2. 不修改仓库；
3. 不把讨论内容自动视为项目事实；
4. 若讨论结果需要落库，应再按对应任务类型进入流程。

## 4. Plan → Execute → Verify → Commit

Project0 的跨文件修改统一遵循：

```text
Plan -> Execute -> Verify -> Commit
```

### 4.1 Plan

Plan 是只读分析阶段。

要求：

1. 读取相关文件；
2. 列出影响范围；
3. 列出允许修改文件；
4. 列出禁止修改文件；
5. 说明风险和验证方式；
6. 不修改文件。

### 4.2 Execute

Execute 是受控修改阶段。

要求：

1. 经人工确认后执行；
2. 只修改批准文件；
3. 不扩大目录和阶段范围；
4. 不顺手重写无关内容；
5. 发现范围不足时暂停并回到 Plan。

### 4.3 Verify

Verify 是修改后检查阶段。

要求：

1. 检查事实一致性；
2. 检查是否存在越界修改；
3. 检查是否遗漏必要同步项；
4. 查看 diff；
5. 必要时运行相关验证命令。

### 4.4 Commit

Commit 是进入版本历史阶段。

要求：

1. 人工先审查 diff；
2. 确认变更符合 CR 或批准范围；
3. 再由人工决定是否提交；
4. 提交后记录必要的 CR 或版本关联。

## 5. 什么时候必须建立 CR

以下情况必须建立 CR：

1. 跨文件修改；
2. 修改事实源；
3. 修改 DEC 状态；
4. 修改架构边界；
5. 修改 `README.md`、`docs/DOC_INDEX.md`、`AGENTS.md`、`CHANGELOG.md` 之间的治理关系；
6. 修改会影响 P1.3 采购、BOM、接线或硬件事实。

CR 应说明变更原因、允许修改范围、禁止修改范围、风险、验证方式和结果。CR 不替代 DEC，也不能绕过人工确认去修改已确认决策。

## 6. Agent 使用红线

Codex / Agent 不得执行以下行为：

1. 未经批准直接修改文件；
2. 自动重写整个 `docs/`；
3. 自动修改已确认 DEC 结论；
4. 自动创建未来目录；
5. 自动推进 P2-P6 或 P7-P10；
6. 在不看 diff 的情况下提交。

如果任务需要突破既定范围，Agent 应先停止执行，说明原因、影响和建议处理方式。

## 7. Git 使用规则

Git 使用规则如下：

1. `main` 是稳定主线；
2. `governance` 是治理分支；
3. 一个主题尽量一个 commit；
4. commit message 使用 `type(scope): description`；
5. 未 push 前可 amend；
6. 合并 `main` 前必须最终验证；
7. 不满意时优先用 `git restore` / `git revert`，不在坏状态上继续手改。

Agent 不应自行执行 `git add`、`git commit`、`git reset`、`git checkout`、`git stash apply` 或 `git stash pop`，除非人工明确授权。
