# 文档治理规范

## 1. 文件作用

本文档用于规定 Project0 文档的事实源、颗粒度、状态、引用和修改边界。

它服务于当前单人 solo 开发和项目全阶段文档治理。本文档不替代项目定义、技术决策、架构设计、BOM、采购清单或实现文档。

## 2. 文档层级

Project0 文档按职责分层管理。

### 2.1 项目定义层

路径：`docs/00_definition/`

职责：

1. 定义项目做什么、不做什么；
2. 定义客观限制、主观需求、迭代边界和成果形态；
3. 作为规划、架构、采购和实现的上游事实源。

### 2.2 P1 规划层

路径：`docs/01_planning/`

职责：

1. 承接项目定义层；
2. 将迭代一范围裁剪成可执行功能、任务和采购前置条件；
3. 为 P1.3 BOM、采购清单、架构展开和 WBS 提供依据。

### 2.3 系统架构层

路径：`docs/02_architecture/`

职责：

1. 承接定义、规划和有效 DEC；
2. 定义系统边界、计算通信边界、电源边界、硬件边界、软件边界和接口边界；
3. 指导部署、实现、配置、硬件资料和测试。

### 2.4 决策事实源

路径：`process/decisions/`

职责：

1. 记录已确认技术决策；
2. 说明决策背景、结论、影响和取舍；
3. 作为规划、架构、实现和采购的重要上游事实源。

### 2.5 项目治理层

路径与文件：

1. `README.md`
2. `CHANGELOG.md`
3. `AGENTS.md`
4. `docs/DOC_INDEX.md`
5. `docs/_meta/`

职责：

1. 提供仓库入口、版本记录、协作规则、索引导航和治理规则；
2. 约束工作方式；
3. 帮助维护文档之间的依赖关系。

### 2.6 变更请求层

路径：`process/change_requests/`

职责：

1. 记录一次变更的原因、范围、风险、验证和结果；
2. 管理跨文件修改和关键治理修复；
3. 防止无边界修改和事实源漂移。

### 2.7 部署 / 实现 / 测试 / 报告层

路径：

1. `docs/04_deployment/`
2. `src/`
3. `firmware/`
4. `hardware/`
5. `config/`
6. `scripts/`
7. `reports/`
8. `presentation/`
9. `experiments/`
10. `simulation/`
11. `data/`

职责：

1. 承接定义、规划、DEC 和架构；
2. 记录部署、实现、配置、硬件资料、实验、报告和展示材料；
3. 不反向定义项目范围或推翻上游事实源。

## 3. 各类文档职责

### 3.1 DEC

DEC 记录已确认技术决策。

规则：

1. 一个 DEC 应聚焦一个关键决策；
2. DEC 应说明背景、结论、影响和取舍；
3. 有效 DEC 是技术决策事实源；
4. 异常、废弃或待复核 DEC 必须标清状态。

### 3.2 CR

CR 记录一次变更的原因、范围、风险、验证和结果。

规则：

1. 一个 CR 只管理一次变更；
2. CR 应明确允许修改和禁止修改；
3. CR 不替代 DEC；
4. CR 不能用来绕过人工确认修改已确认 DEC。

### 3.2.1 CR 流程状态

`process/change_requests/` 下 CR 文件使用流程状态管理一次变更的生命周期，常见状态包括：

1. 草案；
2. 已批准；
3. 执行中；
4. 已完成；
5. 已取消。

这些状态是 CR 生命周期状态，不等同于第 5 节定义的普通文档内容状态。CR 状态口径以 `process/change_requests/CR-000_template.md` 和 `process/change_requests/README.md` 为准。

### 3.3 README

`README.md` 是仓库入口摘要，不是事实源。

规则：

1. 只写当前阶段、项目摘要、目录导航和必要入口；
2. 不单独定义新的项目范围、硬件结论或架构方案；
3. 需要与当前真实状态保持一致。

### 3.4 CHANGELOG

`CHANGELOG.md` 是版本变更记录，不是设计事实源。

规则：

1. 记录版本变化和重要治理变化；
2. 不承载技术决策理由；
3. 不替代 DEC、架构文档或采购文档。

### 3.5 DOC_INDEX

`docs/DOC_INDEX.md` 是文档索引与依赖导航，不替代正式文档。

规则：

1. 说明文档地图、事实源关系和同步检查方向；
2. 不替正式文档下结论；
3. 不把规划中目录描述成当前真实目录。

### 3.6 AGENTS

`AGENTS.md` 是 AI / Agent 协作规则。

规则：

1. 约束 AI、Codex、Agent 和人工协作方式；
2. 说明当前阶段和禁止事项；
3. 不定义新的技术事实。

### 3.7 架构文档

架构文档承接定义、规划和 DEC，不反向推翻事实源。

规则：

1. 只回答对应架构层的问题；
2. 与上游事实源不一致时，应先回到事实源和 DEC 处理；
3. 接口变化必须检查 `interface_definition.md` 和相关下游。

### 3.8 占位文件

占位文件允许存在，但必须不伪装成正式文档。

规则：

1. 内容不足时应标为占位；
2. 不把标题或目录说明当成已完成设计；
3. 后续补全时应按当前阶段和事实源推进。

### 3.9 规划方案文件

规划方案文件必须标清“规划方案”，不能当作当前真实状态。

规则：

1. 可以描述建议目录、建议模块或建议步骤；
2. 不代表仓库已存在；
3. 不代表阶段已完成；
4. 被采纳前不能替代正式文档。

## 4. 单一事实源规则

Project0 采用单一事实源规则。

基本规则：

1. 项目范围事实以 `docs/00_definition/` 为上游；
2. 技术决策事实以有效 DEC 为上游；
3. 架构展开以 `docs/02_architecture/` 为上游；
4. `README.md`、`CHANGELOG.md`、`docs/DOC_INDEX.md` 不能反向定义项目事实；
5. 下游文档应承接和引用，不重复定义上游事实。

处理冲突时：

1. 先识别冲突发生在哪些文件；
2. 再确认哪个文件是上游事实源；
3. 下游文件按上游事实源修正；
4. 如果上游事实源本身需要改变，必须先分析影响范围，必要时建立 CR 或 DEC。

## 5. 文件状态规则

Project0 文件可使用以下状态。

### 5.1 正式

表示内容已确认，可作为当前阶段依据。

处理原则：

1. 下游可以承接；
2. 修改时需要检查影响范围；
3. 涉及关键事实时应有 DEC 或 CR 支撑。

### 5.2 草案

表示内容正在形成，尚未完全确认。

处理原则：

1. 可用于讨论和初步规划；
2. 不直接作为最终执行依据；
3. 转正式前应复核事实源和影响范围。

### 5.3 占位

表示文件已建立，但内容尚不完整。

处理原则：

1. 不作为事实依据；
2. 不伪装成完成状态；
3. 补全时只补当前阶段需要的内容。

### 5.4 废弃

表示文件或结论不再适用。

处理原则：

1. 必须保留可追溯说明；
2. 说明废弃原因和替代来源；
3. 涉及 DEC 状态变化时必须建立 CR。

### 5.5 异常待复核

表示文件存在空文件、冲突、疑似错误或状态不明。

处理原则：

1. 不直接作为事实源；
2. 先标注问题；
3. 经人工确认后再修复、废弃或恢复正式状态。

### 5.6 规划方案

表示内容是建议或设计方案，不等于当前真实状态。

处理原则：

1. 必须清楚标识；
2. 不可当作已创建目录、已完成模块或已采购硬件；
3. 被采纳后再转化为正式文档或任务。

### 5.7 低完成度但有效

表示内容不完整，但已有部分仍能作为局部依据。

处理原则：

1. 保留有效部分；
2. 标注缺口；
3. 不为了补齐形式而扩写未来阶段内容。

## 6. 颗粒度规则

文档颗粒度应服务于可执行和可维护。

规则：

1. 一个 DEC 只记录一个关键决策；
2. 一个 CR 只管理一次变更；
3. 一个架构文档只回答对应架构层问题；
4. `README.md` 只写摘要；
5. `docs/DOC_INDEX.md` 只写索引和依赖；
6. 不把未来阶段内容提前写成当前完成状态；
7. 不为了“完整”而补写 P2-P6 或 P7-P10 内容。

如果一个文件同时承担事实源、索引、执行计划和复盘记录，应在 G0 阶段拆清职责或标注边界。

## 7. 修改规则

文档修改应遵循影响范围和事实源优先原则。

规则：

1. 修改上游事实源前必须先分析影响范围；
2. 修改 DEC 状态必须建立 CR；
3. 跨文件修改必须走 Plan -> Execute -> Verify -> Commit；
4. 修改后必须检查 `README.md`、`docs/DOC_INDEX.md`、`CHANGELOG.md` 是否需要同步；
5. Agent 只能改批准文件。

执行时应避免：

1. 顺手重写无关文件；
2. 把占位文件补成未来阶段完整文档；
3. 在没有 DEC 或 CR 支撑时改变关键事实；
4. 用 README、CHANGELOG 或 DOC_INDEX 反向覆盖上游事实源。

## 8. G0 全项目已有文件规范化收束原则

G0 的目标是让当前已有文件成为 P1.3 和后续阶段的可靠基线。

G0 应做：

1. 复查已有文件；
2. 更正明显错误；
3. 标注文件状态；
4. 对齐事实源；
5. 统一颗粒度；
6. 保留必要的历史脉络；
7. 明确后续需要补全的缺口。

G0 不应做：

1. 补写未来阶段完整内容；
2. 把 P2-P6 或 P7-P10 预期内容写成当前真实状态；
3. 为治理而复杂化治理体系；
4. 用大范围重写代替小步收束；
5. 在未确认影响范围时批量修改已有文件。

G0 完成后的理想状态是：已有文档职责清楚、状态清楚、事实源清楚、依赖关系清楚，后续 P1.3 BOM 与采购清单可以在可靠基线上继续推进。
