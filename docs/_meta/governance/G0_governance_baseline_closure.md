# G0 Governance Baseline Closure

## 文件作用

本文档用于解释 Project0 中 G0 治理基线收束的含义、边界和后续承接方式。

本文档只做历史说明和治理边界说明，不定义新的项目范围、技术事实、架构事实、规划事实、硬件事实、BOM 或采购结论。

## G0 定义

G0 是 Project0 的治理基线收束工作包 / 历史说明，用于描述一轮已经完成的治理入口、文档边界和协作机制收束工作。

G0 不是 P0-P10 的正式阶段，不是新的项目路线阶段，也不是后续阶段推进的前置任务清单。

## G0 与 P0-P10 的关系

G0 不改变 P0-P10 阶段路线，不新增正式阶段，不替代 P0、P1、P2 或其他阶段定义。

P0-P10 的阶段路线、范围和验收口径仍以项目定义、规划文档、有效 DEC 和后续批准的阶段任务为准。

## G0 背景与收束原因

G0 用于在项目继续推进前，对已有治理入口、文档边界、CR 机制、索引和 AI 协作规则做最小收束。

其目标是降低后续 Agent 和人工协作时的误读风险，让项目主线可以回到 P1.3 硬件方案与采购。

## G0 做了什么

G0 主要完成了以下治理收束：

1. 建立或修正最小治理入口。
2. 完成已有文件审计与分类。
3. 对 CR、DOC_INDEX、AGENTS、README、CHANGELOG 等入口进行必要对齐。
4. 形成可支撑 P1.3 回归和后续治理的最小治理基线。

## G0 不做什么

G0 不承担以下职责：

1. 不新增技术事实。
2. 不替代 DEC。
3. 不修改架构事实。
4. 不修改规划事实。
5. 不进入硬件、BOM、采购、源码、固件或部署。
6. 不代表所有遗留问题清零。

## G0 产出与引用关系

G0 相关入口按以下方式理解：

1. `process/change_requests/CR-008_g0_final_governance_cleanup.md` 是 G0 收束执行记录和证据。
2. `docs/DOC_INDEX.md` 是文档导航入口，只索引 G0 历史说明，不复述 G0 全部历史。
3. 本文档是 G0 历史说明入口，用于解释 G0 的含义、边界和承接方式。
4. `README.md` 只保留当前状态快照，不展开 G0 历史。

## G0 后续承接方式

G0 遗留问题继续由后续 CR 或阶段任务承接。

当前主线回到 P1.3。后续治理仍遵守 Plan -> Execute -> Verify -> Commit；跨文件修改必须先有 CR 范围支撑，并且只能修改人工批准的文件清单。

## 使用边界

使用本文档时必须遵守以下边界：

1. 不得把 G0 当成 P0-P10 正式阶段。
2. 不得把 G0 当成当前阶段任务清单。
3. 不得用本文档覆盖 DEC、Architecture、Planning 或硬件事实。
4. 若本文档与 DEC、Architecture、Planning 或硬件事实冲突，应以对应事实源为准，并发起 CR 或 DEC 审查。
